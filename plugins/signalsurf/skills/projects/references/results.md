# Project result presentation

Apply this after choosing an authorized shared writeback under the operating contract. A short answer stays in the ordinary message. A long or reusable deliverable uses a brief conversational reply and one titled Project result document. Keep limitations, decisions and questions needing the member's attention in the reply. Do not paste the whole document into chat as well. Explicit host-only, no-save, no-post or exact-output instructions take precedence; length does not authorize persistence or a new Project.

Discover the live `project_manage` action `post_channel_message` schema and current access. Its optional `input.externalWork` carries `requestSummary` and `document`; when supplying it, include both keys with null for an unused value. The ordinary `message` remains the concise reply and `wakeSurfer` remains false. A completed result is not a delegation request.

- `requestSummary` is a compact client-reported account of the current request, not a verbatim human message. Include only context appropriate for the selected Project audience. Do not export private host transcripts, private reasoning or unrelated User Memory. The server observes MCP operations, not the host's entire conversation; do not promise automatic full-history capture.
- `document` contains `id`, `title`, `content` and `baseRevision`. For a new document, allocate one fresh stable UUID and use null for `baseRevision`. Put the complete deliverable in `content`, with source attribution and caveats intact. Keep operational IDs and request metadata outside sendable copy.
- Publication stores the document and chat contribution atomically under the same operation. Verify the canonical receipt and document revision before claiming a save. An unknown result requires reconciliation; an exact retry reuses the same operation ID, document ID and payload. Do not retry by creating another document.
- Before revising, discover and use `project_query` action `document` with the exact Project, Thread and document selectors required by its live schema. Read the latest content and revision, preserve unrelated text, then publish the same document ID with that observed `baseRevision` and a new operation ID. A stale revision requires reading current state before preparing a new edit. Do not replay the previous document body in chat.

These are native Project writes under existing grants. They do not grant File access, create Knowledge or broaden Memory authority. A denied or unavailable action is a limitation to report, not a reason to create a substitute resource, expand permissions or ask Surfer to bypass it. Finish briefly in the current host with the observed result and any returned canonical link; never invent document URLs or claim an unsaved result is complete.
