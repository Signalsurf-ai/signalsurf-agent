# Sender infrastructure routing

Use Signalsurf's current inventory, module access and shared capacity facts instead of guessing how many Domains or inboxes a Campaign needs. Discover the current live action schemas; an old host tool cache or earlier conversation is not proof that an operation is unavailable.

1. Call `sender_infrastructure_query` action `inspect` to read the authorized Workspace's Domains, exact IDs and names, inboxes, health, usage, renewal terms and readiness. Granted module access uses the same included capacity as paid access; do not infer that the member needs a legacy subscription tier.
2. When audience size, touches and sending days are known, call action `plan_capacity`. Treat per-inbox rate, utilization and inboxes per Domain as editable assumptions. For new Domains, use `search_domains` for live availability and exact quotes, then `setup` intent `domains` for the chosen basket. Registration contact and payment stay in the protected flow.
3. To create inboxes on existing ready Domains, use `sender_manage` action `create_mailboxes` when the live schema exposes it. Supply exact owned `domainId` and `domainName`, the aliases for each Domain and the connection choice in one request. Confirm the whole set through native approval. Included Email sender capacity controls connections only. Managed hosting requires a paid order or an explicit infrastructure grant; an unfunded request returns a protected purchase link and must not create inboxes. Follow returned capacity, Admin and provider restrictions; never bypass them with raw provider calls.
4. When the member wants a link, use `sender_infrastructure_query` action `setup` with `intent: service_basket`, the full Domain/alias basket, warm-up slot quantity and connection choice. Omit Domain ID for new registrations; include the exact owned ID for existing Domains. Return one combined link instead of separate links for every Domain. Opening it only prepares a protected order review; the member confirms the entire basket in Signalsurf. Legacy `mailboxes` intent with one inventory Domain ID remains available when aliases have not been chosen. Never request or relay registrant contact, billing details, passwords or other credentials in the host conversation.
5. To change future renewal preferences, use `sender_manage` action `set_domain_autorenew` with exact owned IDs, names and the inspected `renewalPeriodEnd`, plus the requested enabled state. It requires native approval and current billing authority; it does not purchase a renewal immediately. A changed term or renewal already in progress requires another inspection.
6. Read every per-Domain outcome and retain operation IDs. A partial failure is not whole-batch success. Pending or uncertain creation requires inspection and reconciliation of the existing order; never change aliases or create a replacement purchase to retry. Resume only the exact request when the native continuation permits it.
7. After creation or Web continuation, inspect again. Payment, inbox creation, connection and sending readiness are separate observations. Do not prepare or start an Email Campaign until current authentication, health, capacity and required approvals support it.

If an action is missing, refresh live capability discovery before reporting the exact unavailable operation. Updating the Plugin does not deploy the server or expand an OAuth grant; follow an explicit scope-upgrade response when required.

Warm-up and Placement Test results are evidence, not guarantees. A fixed Domain/inbox ratio or elapsed warm-up period does not guarantee inbox placement.

For monthly volume, use `plan_capacity` with `demandSource: monthly`, `monthlyMessages`, the accepted preparation days and whether warming is included. Ask about the launch deadline and tolerance for waiting. Retain existing senders' observed limits and health, distinguish connection capacity from paid services, and compare feasible preparation/ramp alternatives. USD5 monthly hosting and USD15 monthly warming are separate lines; standard domain registration is USD20 for one year. Quote chosen names before payment. A heat score has no guaranteed date. Check `connectionCapacity.sufficient` before recommending a purchase. A shortfall requires an authorized Workspace capacity adjustment; paying for inbox hosting does not increase connection allowance. Unknown capacity must be refreshed, not treated as sufficient.

Use setup intent `service_order` to resume an exact existing order. Inspect `view: purchases` with its order ID to separate payment, partial fulfillment and provider capacity confirmation. Never treat an active Stripe subscription alone as evidence of a paid invoice. Use `sender_manage` action `update_settings` with `syntheticWarmup` for provider warming lifecycle/settings; the legacy `warmup` boolean adjusts real-send ramping only.

For warming management, inspect `view: warmup` before proposing changes. Compare each inbox's score, score timestamp, provider observation, pending operation and slot status. Refresh stale evidence with `update_settings.syntheticWarmup.action: sync`; a stale or missing score is unknown. Available slots are Workspace-wide and exclude reserved or ambiguous allocations. The planner reuses verified, unoccupied paid/granted slots before estimating additional warming purchases.

Use `syntheticWarmup.action: configure` for provider settings and `pause`, `resume`, `stop` or `connect` for individual lifecycle changes. This does not enable automated Campaign sending. To replace an allocation, use `action: transfer` with a stable `requestId`, source `accountId` and prepared idle `targetAccountId`. Authorize non-managed targets before transferring. Both inboxes remain intact; wait for source release and fresh target confirmation before reporting completion. Re-inspect unresolved transfers and retry the same IDs after interruptions. `action: close_transfer` closes only the exact inspected transfer after both inboxes are reconciled and the target is confirmed stopped; it does not restart the source or cancel billing. Never work around a transfer reservation by starting a separate lifecycle action or buying another slot.

Inspect `view: purchases` without an order ID to discover existing purchases before recreating a lost checkout. Use the exact order ID for detailed read-back and its protected continuation link. Keep cancelled renewal, paid coverage, provider payment and delivered infrastructure separate in the explanation.
