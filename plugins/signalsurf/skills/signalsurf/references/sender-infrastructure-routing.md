# Sender infrastructure routing

Use Signalsurf's current inventory, module access and shared capacity facts instead of guessing how many Domains or inboxes a Campaign needs. Discover the current live action schemas; an old host tool cache or earlier conversation is not proof that an operation is unavailable.

1. Call `sender_infrastructure_query` action `inspect` to read the authorized Workspace's Domains, exact IDs and names, inboxes, health, usage, renewal terms and readiness. Granted module access uses the same included capacity as paid access; do not infer that the member needs a legacy subscription tier.
2. When audience size, touches and sending days are known, call action `plan_capacity`. Treat per-inbox rate, utilization and inboxes per Domain as editable assumptions. For new Domains, use `search_domains` for live availability and exact quotes, then `setup` intent `domains` for the chosen basket. Registration contact and payment stay in the protected flow.
3. To create inboxes on existing ready Domains, use `sender_manage` action `create_mailboxes` when the live schema exposes it. Supply exact owned `domainId` and `domainName`, the aliases for each Domain and the connection choice in one request. Confirm the whole set through native approval. Included Email sender capacity requires no separate checkout. Follow returned capacity, Admin and provider restrictions; never bypass them with raw provider calls.
4. When the member wants a link, use `sender_infrastructure_query` action `setup` with `intent: mailbox_batch` and the same full Domain/alias basket and connection choice. Return one combined link instead of separate links for every Domain. Opening it only prepares an independent review dialog; the member confirms the entire basket in Signalsurf. Legacy `mailboxes` intent with one inventory Domain ID remains available when aliases have not been chosen. Never request or relay registrant contact, billing details, passwords or other credentials in the host conversation.
5. To change future renewal preferences, use `sender_manage` action `set_domain_autorenew` with exact owned IDs, names and the inspected `renewalPeriodEnd`, plus the requested enabled state. It requires native approval and current billing authority; it does not purchase a renewal immediately. A changed term or renewal already in progress requires another inspection.
6. Read every per-Domain outcome and retain operation IDs. A partial failure is not whole-batch success. Pending or uncertain creation requires inspection and reconciliation of the existing order; never change aliases or create a replacement purchase to retry. Resume only the exact request when the native continuation permits it.
7. After creation or Web continuation, inspect again. Payment, inbox creation, connection and sending readiness are separate observations. Do not prepare or start an Email Campaign until current authentication, health, capacity and required approvals support it.

If an action is missing, refresh live capability discovery before reporting the exact unavailable operation. Updating the Plugin does not deploy the server or expand an OAuth grant; follow an explicit scope-upgrade response when required.

Warm-up and Placement Test results are evidence, not guarantees. A fixed Domain/inbox ratio or elapsed warm-up period does not guarantee inbox placement.
